# Guided Interview Reference

Use this reference for the Guided Interview mode. Conduct the interview in the user's language. These are question banks, not a script to recite mechanically.

## Interview Principles

1. Ask three to five focused questions per stage.
2. Skip questions already answered by the user or available context.
3. Offer concrete options and recommendations, while allowing free-form answers.
4. Summarize what each stage implies before moving on.
5. Record explicit decisions separately from reasonable defaults.
6. Challenge premature complexity: do not begin with search engines, plugins, or automation unless the user's requirements justify them.
7. Do not create a repository until the final blueprint has been explicitly confirmed.

## Stage 1: Background, Purpose, and Success

Establish:

- What repeated cost or lost value should the wiki reduce?
- Is the primary goal retrieval, reusable methodology, content production, decision traceability, self-understanding, or something else?
- Does the user want one connected personal wiki, a topical research wiki, a work archive, or a public methodology base?
- Which domains belong in the first iteration?
- What single outcome would make the wiki worthwhile?

Useful prompts:

- "What problems should this knowledge base solve for you?"
- "What should it help you do differently six months from now?"
- "Which result matters most: sourced answers, reusable frameworks, better outputs, or understanding why your judgments changed?"

Recommended default when the user has no preference: optimize for traceable judgments and reusable understanding rather than storage volume.

## Stage 2: Knowledge Objects, Sources, and Boundaries

For each initial domain, establish:

- What should accumulate: concepts, research records, strategies, experiences, principles, decisions, relationships, health, habits, or other objects?
- Which raw sources will enter: books, articles, papers, web clippings, journals, voice transcripts, AI conversations, reports, datasets, project files, or images?
- What must never enter the repository?
- Should the wiki be private, public, or private with manually sanitized exports?

Useful prompts:

- "What counts as valuable knowledge in this domain?"
- "Which materials will become raw sources?"
- "What should remain outside the knowledge base even if the repository is private?"

Recommended default: private repository, broad raw-source support, no credentials or unnecessary third-party personal data, and manual public export.

## Stage 3: Capture, Workflow, and Agent Authority

Establish:

- How capture happens: one source at a time, themed batches, an always-open inbox, or a mixed model.
- Which devices and applications matter.
- Which pages the agent may update automatically.
- Which changes require user confirmation.
- How contradictory evidence should affect an existing judgment.
- When valuable chat output returns to the wiki.

Useful prompts:

- "What is the least friction you can sustain for daily capture?"
- "May the agent rewrite current judgments, or should it propose changes first?"
- "Should valuable answers be archived automatically, only on command, or both?"

Recommended default:

- Mixed capture: quick inbox notes plus themed research batches.
- Automatic updates for source, concept, and entity pages.
- Confirmation for established claims, principles, and important decisions.
- Preserve old judgments and record why they changed.
- Support both agent-selected archival and an explicit `Archive` command.

## Stage 4: Taxonomy, Evidence, and Outputs

Establish:

- Primary navigation: domains, long-term questions, knowledge types, or chronology.
- Core and supporting page types.
- How to distinguish facts, external viewpoints, user judgments, and AI inference.
- Which outputs the wiki should support first.
- How much citation and metadata rigor is useful without becoming burdensome.

Recommended default:

- Domain navigation with type indexes.
- Core pages: `claim`, `principle`, `decision`, and `question`.
- Supporting pages: `source`, `concept`, `entity`, and `review`.
- Explicit source dates and human-readable judgment history.
- Private outputs by default; public outputs require a separate sanitization step.

Do not force every page type on the user. Explain whether an omitted type is excluded or retained only as a lightweight supporting page.

## Stage 5: Pilot, Tooling, and Delivery

Establish:

- Which small batches can validate two complete workflows.
- Whether the user will browse with Obsidian, an editor, GitHub, or only an agent.
- Whether mobile capture is required.
- Whether the first version should be pure Markdown or include scripts.
- Whether delivery should stop at a blueprint, create a local repository, or create a remote repository.

Recommended default:

- Two small pilot batches, not a full historical migration.
- Markdown, YAML, bidirectional links, an index, and a log.
- Obsidian as an optional viewer, not a dependency.
- Local scaffolding first when GitHub access is unavailable.

## Final Synthesis

Before asking for confirmation, summarize:

1. The one-sentence purpose.
2. Initial domains and explicit non-goals.
3. Raw-source boundaries and privacy.
4. Core page types and navigation.
5. Capture and archival workflow.
6. Agent permission matrix.
7. Contradiction and judgment-history rules.
8. Outputs and public-export boundary.
9. Pilot scope and acceptance criteria.
10. Repository name, location, visibility, and schema convention.

Ask the user to confirm the complete blueprint. Treat material changes after confirmation as a blueprint revision before scaffolding.
